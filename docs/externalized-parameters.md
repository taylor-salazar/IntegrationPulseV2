# Integration Pulse Externalized Parameters

These parameters are expected on integrations that want to use Integration Pulse's configuration and immediate-run features. The names should be kept exact so the app and CPI Groovy scripts can read them consistently.

| Parameter | Purpose | Example value |
| --- | --- | --- |
| `SFResourcePath` | SuccessFactors OData entity/resource used as the starting point for the immediate-run selection screen. Integration Pulse uses this to know which EDMX entity to browse, such as `EmpJob` or `EmpEmployment`. | `EmpJob` |
| `filter.query` | The original saved SuccessFactors query for the integration's normal scheduled/deployed behavior. Integration Pulse treats this as the baseline query and will not let immediate-run users remove fields/navs already included here. | `$select=userId,startDate,eventReason,companyNav/name&$expand=companyNav&$filter=...` |
| `pulse.immediateRunEndpoint` | HTTPS sender endpoint used by **Run Immediately**. This points to the separate sender flow that starts the integration without changing timer parameters. If entered without `/http`, Pulse normalizes it before calling Integration Suite. | `/IntegrationPulse/IPEndpointTest` |
| `pulse.immediateRunSupported` | Feature flag that controls whether the **Run Immediately** button appears. Use `true` only when the integration has the separate HTTPS sender flow configured. | `true` |
| `pulse.Source` | Source application/system type. Integration Pulse uses this to decide whether SuccessFactors-specific features should show, such as EDMX upload and entity field selection. | `SuccessFactors` |
| `filter.pulseQuery` | Immediate-run override query generated by Integration Pulse. Pulse sends this as an HTTP header only when the user adds fields/navs/filters beyond `filter.query`. In CPI, a Groovy script can copy the header into this exchange property. | `$select=userId,startDate,eventReason,customString1&$expand=companyNav&$filter=...` |
| `filter.SFQuery` | Final query property used by the SuccessFactors adapter. CPI Groovy should set this to `filter.pulseQuery` when present; otherwise it should fall back to `filter.query`. | Same shape as `filter.query` or `filter.pulseQuery` |

## Recommended Runtime Flow

1. Store the standard integration query in `filter.query`.
2. Set `pulse.immediateRunSupported=true` only for integrations with a separate HTTPS sender.
3. Set `pulse.immediateRunEndpoint` to that sender address.
4. Set `pulse.Source=SuccessFactors` when the source is SuccessFactors and EDMX-based field selection should be available.
5. During an immediate run, copy the incoming Pulse query header into `filter.pulseQuery`.
6. Set `filter.SFQuery` from `filter.pulseQuery` if it exists, otherwise from `filter.query`.

## Header Names Sent by Integration Pulse

For testing, Integration Pulse sends the generated immediate-run query under these equivalent headers:

```text
filter.pulseQuery
filter-pulseQuery
X-Pulse-Query
```

If no fields/navs/filters were added by the user, Integration Pulse sends none of these headers. In that case, CPI should use the original `filter.query`.

In CPI runtime configuration, make sure custom inbound headers are allowed. A practical allowed-header value is:

```text
X-Pulse-Query|filter-pulseQuery|filter.pulseQuery
```
