## PRODUCT BEHAVIOR CLARIFICATION REQUIRED

**QA-22 — Medium, baseline options outside select/expand/filter.** Local execution proves adding a field drops `$top=25` and `fromDate=2026-01-01`. One interpretation: an additive override must preserve the entire baseline query, including paging and SF date parameters. Another: this product only supports `$select`, `$expand`, `$filter`; other options must be rejected or kept outside this override. Documentation describes those three but does not define the others. The preserved assertion tests the lossless interpretation and is **provisional**, not proof of a violated approved API contract. Proposed change if approved: retain unknown option/value pairs through merge/serialization; otherwise explicitly reject unsupported baselines. Evidence: `reliability.test.cjs`, QA-22; `_parsePulseQuery` and `_formatPulseQueryParts`.

Other product decisions needed before implementing fixes: whether duplicate log IDs count once; whether warning/unknown runtime statuses should ever display as passed; whether feature-flag aliases `yes`, `y`, `1` are intentionally supported beyond documented `true`; how to display unavailable 24-hour counts; and what to do when multiple design-time artifacts plausibly match. Current behavior is documented in the coverage matrix rather than silently redefined by this audit.

## Additional inferred release risks

- No authentication/authorization enforcement exists in FastAPI itself, including Deploy, trigger and payload ingestion/download. README explicitly leaves SSO wiring to deployment. Actual BTP/approuter protection must be verified; CORS alone is not authentication. This amplifies QA-13 if the proxy is reachable by untrusted clients.
- Destination configuration fallbacks catch *all* errors and may retry all identities on 401/403/429/timeouts. Proxy loops catch all HTTP status errors. An authorization or service failure can be mislabeled “not found.” Do not add more fallbacks without exact live URLs/responses.
- Proxy candidate IDs and versions are independently deduplicated and crossed; `Active` precedes explicit design-time version, unlike destination mode. Package singleton fallback can choose an unrelated item; normalized/fuzzy multiple matches choose the first successful request. This is an unproven identity assumption, especially for writes.
- Review state is intentionally local to browser/origin. Persistence failure logs a warning but controllers optimistically mark review/resolution state successful. Cross-tab and multi-user consistency are not implemented. No production change is implied by testing this documented local-store model.
- Arbitrary payload media types are accepted, and `nosniff` is not set on attachment responses. Storage is full-text and receiver has no application size cap. Preview limit controls display, not ingestion/memory limits.
- Header values from pulse query/entity are not explicitly validated/encoded for CR/LF/non-ASCII. Browser/httpx rejection and sender acceptance need focused compatibility tests with an approved representation; current ASCII sample successes do not prove Unicode header transport.
- Detail, Home, Monitoring and Monitoring Detail have overlapping-load/lifecycle risks beyond the reproduced Detail race. Catalog token guards cover only some paths; cached initial responses and background completion updates bypass some stale checks. Dialog Fragment/FileReader completion after close is not guarded throughout.
- Ordinary parameter editor is a single-line Input even for multiline values; several timer subcontrols lack the enclosing parameter's read-only binding. Static concern only; actual UI behavior must be checked.
